# Merge vectors

One case per directory, named for what it establishes. A case holds the reports a merge reads, the schema versions the caller accepts, the facts the caller supplies, and either the merged report the merge returns or the exit code with which the run ends before any merged report exists, so two implementations of the merge are tested against declared data rather than against each other. The algorithm the cases exercise is the one [`merge.md`](../../contract/grammar/merge.md) states.

## The files of a case

| File | What it holds |
| --- | --- |
| `inputs/<nn>-<language>.json` | one input report, an instance of [`report.schema.json`](../../contract/report.schema.json) |
| `inputs/<nn>-<language>.facts.json` | the facts document the analyzer of `inputs/<nn>-<language>.json` wrote beside it, an instance of [`facts.schema.json`](../../contract/facts.schema.json); absent where the run asked for none |
| `accepted.txt` | the schema versions the caller accepts, on one line, in ascending order and separated by single spaces |
| `caller.json` | the facts the caller supplies: the merging product's identity, the schema and contract versions it writes, the artifact digest of each input report, the lowest severity that fails the run, and the run's minimum confidence |
| `expected.json` | the merged report, byte for byte |
| `expected_exit` | the exit code, one integer from [`exit-codes.json`](../../contract/exit-codes.json) |

An input file's name is a two-digit ordinal, a hyphen and the language of the analysis the report carries, and a facts document takes its report's name with `.facts.json` in place of `.json`. The ordinal orders the files of the directory and means nothing to the merge, which returns the same report and the same exit code whatever order it reads its inputs in; a case whose two reports carry one language numbers them both for that language.

`caller.json` is one object with five members and an optional sixth: `schema_version` and `contract_version`, the versions the merged report is written to; `analyzer`, the merging product's `name`, `version` and `conformance` block in the shape [`report.schema.json`](../../contract/report.schema.json) gives those three members; `digests`, one member per file under `inputs/`, named for the file, whose value is the digest of the analyzer artifact that wrote that report; `fail_on`, one of `allow`, `warn` and `deny`, the lowest severity at which a finding fails the run; and `min_confidence`, one of `certain`, `probable` and `possible`, the run's `analysis.min_confidence`, below which binding rule 3 withholds a schema finding, absent where the caller withholds none. Every case carries one, a case the merge refuses before it builds a report included, because the caller hands the facts over with the reports.

Every case carries `expected_exit`. A case carries `expected.json` only where the merge produces a merged report: a report the admission step refuses, and a pending finding that meets no evaluation of its edge's other side, each end the run with the failure code before a merged report exists, and those cases hold `expected_exit` alone.

## Running a case

Decode every report under `inputs/`, take the accepted range from `accepted.txt` and the caller's facts from `caller.json`, and merge. Compare the exit code with `expected_exit`, and where the case carries one, compare the bytes of the merged report with `expected.json`. Every byte of `expected.json` follows from those three inputs and the steps of `merge.md`: no member of a merged report comes from anywhere else.

`expected.json` is compared as bytes, so it is written in the encoding a merged report is written in: UTF-8, a line feed as the line ending, two-space indentation, one member or array element to a line, an empty array or object on one line, one trailing newline, and the members of every object in the order `report.schema.json` declares them. Every array is in the order that schema states for it, which for `findings`, `stale_suppressions` and `declared_gaps` is the canonical key. A number is written as its decimal digits. Inside a string, `"` and `\` are written `\"` and `\\`; U+0008, U+0009, U+000A, U+000C and U+000D are written `\b`, `\t`, `\n`, `\f` and `\r`; every other character below U+0020 is written `\u00` and two lowercase hexadecimal digits; U+2028 and U+2029 are written `\u2028` and `\u2029`; and every other character, `/`, `<`, `>` and `&` included, is written as itself. An input report may hold U+2028 and U+2029 unescaped, as an ECMAScript `JSON.stringify` writes them, and the merged report still writes the escapes, so its bytes do not depend on which product wrote an input.

## What the merged reports hold

Step 6 of [`merge.md`](../../contract/grammar/merge.md) states every member. `analyzer` names the merging product from `caller.json`, with the union of the inputs' languages and the range `accepted.txt` names; `merged_from` names every input report with the digest `caller.json` gives it; and a finding, a stale suppression, a declared gap and an edge evaluation carry the name of the analyzer whose report carried them, while a finding the merge itself emits carries none. `totals.deletable_lines` is the sum of `deletable_lines` over the distinct components the root findings name, each component counted once however many of its root findings the report holds, and `totals.omitted` is 0, because no input report omits a finding.

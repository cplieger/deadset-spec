# Conformance corpus

A fixture lives under `corpus/fixtures/<name>/` and holds one rendering per language: a Go rendering is one `go.txtar` archive holding the target and consumer modules as sections, and a TypeScript rendering is a `ts/` directory. An analyzer loads a rendering and analyzes it exactly as it would a real repository. One expectation file, `expect.json`, sits beside the renderings and names, in a language-neutral form, which findings an analyzer must report and which it must not report, per issue kind and per exemption class. In a Go rendering each consumer module requires the target module and carries a `replace` directive naming the target's path relative to the consumer directory, `../target`, so the rendering loads with no network access. A Go rendering may also carry a dependency directory, a second local module the target's own module file requires and replaces with `../<dependency>`; the expectation file names its consumers and every other directory at the rendering root is a dependency, so a run resolves the requirement from the rendering and loads the directory as part of the target's build list rather than as a consumer. Each rendering's manifest, `fixture.json`, binds every logical name the expectation file uses to a file and a line in that rendering, and declares the build matrix a run derives from the rendering where the rendering has one, which is what an expectation's configuration list is drawn from. An expectation may also name the kind of subject its finding is about, drawn from the `symbol.kind` vocabulary of [`../contract/finding.schema.json`](../contract/finding.schema.json); a runner then checks the reported finding's own subject kind against it and reads that schema's rule on the liveness relation from it, so a row whose subject kind or whose code that schema names as carrying no relation expects a finding with no relation, and a row naming neither expects one. A row that names no subject kind is answered without either check, so the member changes nothing for a fixture that omits it. A fixture may also declare the world its run is answered under, by naming in `closed_world` the facts the runner asserts to the analyzer: `consumers` that the consumer set the fixture names is complete, `matrix` that the manifest's build matrix is every configuration the target builds, which a runner configures from the manifest because a matrix a run derives is never a complete one. A runner sets the configuration key each named fact carries and leaves it at its default otherwise, so a fixture that declares neither is analyzed under the open world, where a kind whose precondition is a complete world reports nothing. A runner answers each fixture in two phases, and the second one has a narrower population than the first: a reported finding is written into the rendering's ignore file and the rendering is analyzed again only where the finding's subject is a declaration or a part of one, because a record of the suppression grammar binds to a declaration and a finding about a requirement, a directive, a file, a suppression record, a root or an edge has none to bind to. A declared gap is a value an analyzer writes into its conformance report for a capability it does not implement; an expectation that is neither answered nor declared fails the analyzer, so a gap is reported rather than omitted. An analyzer commits `conformance.json`, its declared gaps, and its corpus runner writes `conformance-results.json`, both against the schemas in this directory.

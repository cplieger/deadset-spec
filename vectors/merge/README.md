# Merge vectors

One case per directory, named for what it establishes. A case holds the reports a merge reads, the schema versions the caller accepts, the facts the caller supplies, and either the merged report the merge returns or the exit code with which the run ends before any merged report exists, so two implementations of the merge are tested against declared data rather than against each other. The algorithm the cases exercise is the one [`merge.md`](../../contract/grammar/merge.md) states.

## The files of a case

| File | What it holds |
| --- | --- |
| `inputs/<nn>-<language>.json` | one input report, an instance of [`report.schema.json`](../../contract/report.schema.json) |
| `accepted.txt` | the schema versions the caller accepts, on one line, in ascending order and separated by single spaces |
| `caller.json` | the facts the caller supplies: the merging product's identity, the schema and contract versions it writes, the artifact digest of each input report, and the lowest severity that fails the run |
| `expected.json` | the merged report, byte for byte |
| `expected_exit` | the exit code, one integer from [`exit-codes.json`](../../contract/exit-codes.json) |

An input file's name is a two-digit ordinal, a hyphen and the language of the analysis the report carries. The ordinal orders the files of the directory and means nothing to the merge, which returns the same report and the same exit code whatever order it reads its inputs in; a case whose two reports carry one language numbers them both for that language.

`caller.json` is one object with five members: `schema_version` and `contract_version`, the versions the merged report is written to; `analyzer`, the merging product's `name`, `version` and `conformance` block in the shape [`report.schema.json`](../../contract/report.schema.json) gives those three members; `digests`, one member per file under `inputs/`, named for the file, whose value is the digest of the analyzer artifact that wrote that report; and `fail_on`, one of `allow`, `warn` and `deny`, the lowest severity at which a finding fails the run. Every case carries one, a case the merge refuses before it builds a report included, because the caller hands the facts over with the reports.

Every case carries `expected_exit`. A case carries `expected.json` only where the merge produces a merged report: a report the admission step refuses, and a pending finding that meets no evaluation of its edge's other side, each end the run with the failure code before a merged report exists, and those cases hold `expected_exit` alone.

## Running a case

Decode every report under `inputs/`, take the accepted range from `accepted.txt` and the caller's facts from `caller.json`, and merge. Compare the exit code with `expected_exit`, and where the case carries one, compare the bytes of the merged report with `expected.json`. Every byte of `expected.json` follows from those three inputs and the steps of `merge.md`: no member of a merged report comes from anywhere else.

`expected.json` is compared as bytes, so it is written in the encoding a merged report is written in: UTF-8, a line feed as the line ending, two-space indentation, one member or array element to a line, an empty array or object on one line, one trailing newline, and the members of every object in the order `report.schema.json` declares them. Every array is in the order that schema states for it, which for `findings`, `stale_suppressions` and `declared_gaps` is the canonical key. A number is written as its decimal digits. Inside a string, `"` and `\` are written `\"` and `\\`; U+0008, U+0009, U+000A, U+000C and U+000D are written `\b`, `\t`, `\n`, `\f` and `\r`; every other character below U+0020 is written `\u00` and two lowercase hexadecimal digits; U+2028 and U+2029 are written `\u2028` and `\u2029`; and every other character, `/`, `<`, `>` and `&` included, is written as itself. An input report may hold U+2028 and U+2029 unescaped, as an ECMAScript `JSON.stringify` writes them, and the merged report still writes the escapes, so its bytes do not depend on which product wrote an input.

## What the merged reports hold

Step 6 of [`merge.md`](../../contract/grammar/merge.md) states every member. `analyzer` names the merging product from `caller.json`, with the union of the inputs' languages and the range `accepted.txt` names; `merged_from` names every input report with the digest `caller.json` gives it; and a finding, a stale suppression, a declared gap and an edge evaluation carry the name of the analyzer whose report carried them, while a finding the merge itself emits carries none. `totals.deletable_lines` is the sum of `deletable_lines` over the distinct components the root findings name, each component counted once however many of its root findings the report holds, and `totals.omitted` is 0, because no input report omits a finding.

## What the cases establish

| Case | What it establishes | Exit |
| --- | --- | --- |
| `configuration-built-and-not-built` | One report built a configuration that another report derived and could not build. Admission refuses the pair, because one identifier names one configuration of a run, built or dropped. | 3 |
| `configuration-entries-differ` | Two reports carry one configuration identifier with two different build-tag lists. Admission refuses the pair, because one identifier names one configuration of a run. | 3 |
| `configuration-not-built-errors-merged` | Two reports derive one configuration, fail to build it, and word the error two ways. The entries agree on every identity member, so the merge carries one entry under the identifier, with the error of the report `merged_from` names first. That report is the second input file, so a merge that keeps the first entry it reads carries the other error. | 1 |
| `conformance-not-passed` | An input report whose conformance result is not a pass. Admission refuses it, and the findings it holds are never presented. | 3 |
| `consumer-entries-differ` | Two reports load one consumer identifier from two different paths. Admission refuses the pair, because one identifier names one consumer of a run. | 3 |
| `consumer-loaded-and-unavailable` | One report loaded a consumer that another report names as unavailable. Admission refuses the pair, because one identifier names one consumer of a run, loaded or unavailable. | 3 |
| `consumer-unavailable-reasons-merged` | Two reports name one consumer as unavailable and word the reason two ways. The entries agree on every identity member, so the merge carries one entry under the identifier, with the reason of the report `merged_from` names first. That reason sorts after the other bytewise and its report is the first input file, so a merge that keeps the least reason, or the last entry it reads, carries the other. | 1 |
| `edge-absent-on-every-side` | Both sides of a declared edge hold an evaluation and every one of them is `absent`. The merge emits one stale-edge finding for the edge, at the fixed position of a document-level finding, and carries both evaluations. | 1 |
| `fail-on-warn` | A caller whose `fail_on` is `warn`, and one report whose one finding carries the `warn` severity. The run fails on that finding; under the default `fail_on`, `deny`, the same report would pass. | 1 |
| `findings-omitted` | A report whose configured maximum kept a finding out of its `findings` array. Admission refuses it, because a merge reads every finding an analysis produced. | 3 |
| `line-separators-escaped` | A report written as `JSON.stringify` writes one, holding U+2028 and U+2029 unescaped in a member's string-literal key. The merged report writes both as escapes, wherever the key appears. | 1 |
| `one-analyzer-name-twice` | Two reports one analyzer name wrote at two versions, from two artifacts the caller gives two digests for, each over its own build configuration and each naming its finding's component `deadset-go/c-1`. Admission refuses the pair whatever the versions and digests, because an analyzer's name prefixes the component identifiers it mints and names the analyzer of every record the merged report carries from it. A merge that refuses only one artifact run twice, or one name at one version, admits these. | 3 |
| `one-artifact-run-twice` | Two reports one analyzer artifact wrote, each over its own build configuration: one analyzer name, one version and one digest the caller gives for both. Admission refuses the pair, because the two carry one analyzer name. The two reports differ, so a merge that refuses only two equal reports admits these. | 3 |
| `one-report` | One report and no edge. The merged report carries the input's finding under the analyzer that reported it, names that analyzer in `merged_from`, and recomputes the totals. | 1 |
| `pending-member-beside-a-stale-edge` | One report holds two `dead` evaluations of one component: the root's, whose paired side is `absent`, and a member's on a second edge, whose paired side is `dead`. The stale edge drops the component, the member's evaluation then reads as `live`, and the symbol paired with the member is dropped too, not promoted. That symbol's finding comes first in canonical order, so a merge that visits the evaluations in that order drops it only on a second pass. The merged report holds the stale-edge finding alone. | 1 |
| `pending-member-on-a-second-edge` | One report holds two `dead` evaluations of one component: the root's, whose paired side is `live`, and a member's on a second edge, whose paired side is `dead`. The live pair drops the component, the member's evaluation then reads as `live`, and the symbol paired with the member is dropped too. That symbol's finding comes first in canonical order, so a merge that visits the evaluations in that order drops it only on a second pass. The merged report holds no finding, and its deletable lines count none of the root's. | 0 |
| `pending-pair-absent` | One side is `dead`, its report carries a finding that falls with the pending one, and the paired side is `absent`. Both findings are dropped, and the merge emits one stale-edge finding for the edge and carries the absent evaluation alone. | 1 |
| `pending-pair-dead` | Both sides of an edge are `dead`. Both findings are promoted, their components are unioned under the identifier the canonical order reaches first, and the finding carried from the same report as a unioned component takes that identifier and the summed counts. | 1 |
| `pending-pair-live` | One side is `dead`, its report carries a finding that falls with the pending one, and the paired side is `live`. Both findings are dropped, and the merged report holds the live evaluation, no finding and no pending count. | 0 |
| `pending-pair-unevaluated` | A `dead` evaluation whose edge no other report evaluates. The merge ends the run on the unresolved edge. | 3 |
| `schema-version-out-of-range` | A report whose schema version is outside the accepted range. Admission refuses it before any other step. | 3 |
| `stale-suppression-carried` | A report holding one stale suppression and no finding. The merge carries the record, and the run fails on it. | 1 |
| `targets-differ` | Two reports whose targets name two different roots. Admission refuses the pair before any other step, because a merged report names one target. | 3 |
| `test-file-rule-counted-two-ways` | Two analyzers claim one language and count one test-file rule differently, one matching 9 files and the other 10. The merged report holds one entry per distinct entry, so it carries both, ordered by rule and then by the bytewise comparison of their encodings, which puts the count 10 first. The first input file holds the count 9, so a merge that keeps one entry per rule, keeps the order it reads its inputs in, or orders the counts as numbers writes another array. | 0 |
| `two-analyzers-one-language` | Two analyzers claim one language and report one finding in common. Both records survive, adjacent and ordered by the name of the analyzer that carried each. | 1 |
| `two-reports-no-edges` | Two reports of two languages and no edge. Every finding is carried, and the merged order interleaves the two languages by path. | 1 |
